# Edify — Platform KPI Audit and Metric Registry (2026-07-27)

> Historical foundation audit. The current presentation and decision inventory
> is [kpi-simplification-audit-2026-08-20.md](kpi-simplification-audit-2026-08-20.md)
> with machine-readable detail in `platform-kpi-inventory.json`.

Response to the platform-wide mandate to make every KPI unique, correct,
traceable, role-appropriate and backed by a canonical service.

This document records **what was measured, what was found, what was fixed, and
what remains**. It does not claim the mandate is complete — section 8 below
states plainly what is still outstanding, because the remaining surface is
large and reporting it as done would be false.

---

## 1. Method

The KPI surface was too large to audit by reading: 875 templates and 716
modules. So the audit is driven by a scanner that derives its facts from the
source, now committed as a permanent tool:

```bash
python manage.py build_kpi_inventory
```

It writes `docs/platform-kpi-inventory.json` and is covered by
`apps/system_health/test_kpi_inventory.py`.

### A correction to the method, made during the audit

The first version of the scanner counted every dict carrying `label` plus a
value-ish key. That over-reported badly. It flagged `"Returned"` as a
five-way-duplicated KPI — but four of those five are **status-bucket rows**
(`{"label": …, "amount": …}`) from `weekly_status_buckets`, one shared
vocabulary correctly rendered in several places. `finance_operating_views.py`
*imports* that bucketing from `disbursement_dashboard_service.py`; it does not
redefine it. Counting it as a defect would have sent someone to "fix" working
code.

The committed scanner therefore classifies rather than lumps:

| Kind | Shape | Treatment |
|---|---|---|
| `kpi-tile` | `label` + `value` (+ presentation keys) | audited as a KPI |
| `breakdown-row` | `label` + `amount`/`count`, no `value` | workflow vocabulary; repeats are legitimate |
| `other` | everything else | ignored |

The classifier itself is tested, because a misclassification sends a reader to
the wrong conclusion in both directions.

A note on how to read the tile count: this is a *source* scan of hand-written

"registered". 281 → 272 is My Plan's eight tiles plus the deleted duplicate on

The headline is the third row. With no identity on any tile, nothing about the
KPI layer was enforceable: not deduplication, not drill-down agreement, not
role scoping, not cache keys. Every other rule in the mandate depends on a
metric being nameable.

## 3. Defects found and verified

### 3.1 One service read another's numbers by their display label — FIXED

`CDDashboardService.kpis()` reached into `CDAnalyticsService.kpis()` and indexed
by wording:

```python
analytics = {k["label"]: k for k in CDAnalyticsService.kpis(cd, acts)}
target_progress = analytics["Overall Target Achievement"]["value"]
...
analytics["Budget Utilization"]["value"]
```

Rewording either card for clarity would have taken the Country Director
dashboard down with an uncaught `KeyError`. Nothing tested the coupling.

This was proven during the fix: renaming the first key surfaced the *second*
lookup as a live 500 on `/dashboard`, which no existing test had covered.

**Fixed.** Cards now publish a stable `key`; the dashboard addresses them by it.
`apps/analytics/test_kpi_card_keys.py` fails on any Title-Case string subscript
anywhere in `apps/analytics`, and statically checks that every key the dashboard
consumes is one the analytics service publishes.

### 3.2 A finance KPI misstated its denominator — FIXED

`Budget Utilization` on the CD analytics page was captioned **"disbursed /
approved"**. The computation is:

```python
def _budget_utilization(cd):
    requested = int(qs.aggregate(s=Sum("amount"))["s"] or 0)
    disbursed = int(qs.aggregate(s=Sum("disbursed_amount"))["s"] or 0)
    return _pct(disbursed, requested)      # ← requested, not approved
```

The denominator is the **requested** pipeline. Since requested ≥ approved, a
Country Director reading the figure as approved-basis utilisation reads it as
worse than the approved basis actually is. The CD *dashboard* captioned the same
borrowed number correctly ("disbursed vs requested pipeline") — so the two pages
described one number two ways, and the analytics page was the wrong one.

**Fixed**: the caption now reads "disbursed / requested".

### 3.3 One metric family, three date bases — DOCUMENTED, PARTLY FIXED

"Planned This Week / Month / Quarter / FY" and "Completion Readiness" were each
computed independently in `apps/my_plan/services.py` and
`apps/projects/my_plan_service.py`, on **different date bases**:

| Tile | My Plan | Projects |
|---|---|---|
| Week / Month | `planned_date` in range **OR** (`planned_date IS NULL` **AND** `scheduled_date` in range) | strict `planned_date__range` |
| Quarter | stored `quarter` field — not a date filter at all | `planned_date__range` |
| FY | **no date filter** (`qs.count()`) | `planned_date__range` |

They also rounded differently — `int()` truncation against `round()` — so two
of three planned activities read **66%** on one page and **67%** on the other.

The status vocabularies turned out to agree: `DELIVERED_STATUSES` in
`projects/dashboard_service.py` has identical membership to
`COMPLETED_WORK_STATUSES` in `apps/core/activity_types.py`. It is a redundant
re-declaration of an owned constant rather than a live divergence — but it is
exactly the shape that becomes one.

**Partly fixed.** My Plan is migrated onto the registry and each basis is now
*declared* rather than implied (the quarter tile honestly declares
`NOT_TIME_BOUND`, because reading a stored stamp is not a date filter).
Reconciling the bases themselves needs a data-repair pass over `quarter` and is
listed as outstanding.

### 3.4 Missing data rendered as zero, everywhere — FIXED IN THE SHARED PATH

The platform's percentage helper is:

```python
def _pct(n: int, d: int) -> int:
    return round(n / d * 100) if d else 0
```

So an empty denominator produces `0`. "No fund requests exist" and "we requested
money and disbursed none" render identically; a school with no verified SSA
enters intervention averages as a zero rather than as an absence.

**Fixed in the new path.** `MetricValue.ratio()` returns a `NO_DATA` state, and
`render_metric` refuses to render a percentage that cannot name its denominator.
`_pct` itself still has ~40 call sites and is listed as outstanding.

### 3.5 The same amount of money rendered three ways — FIXED

Twelve private compact-UGX formatters exist across the platform. Three were
compared directly:

| Amount | `pl_approval_service._ugx` | `finance_operating_views` | `budget_views` |
|---:|---|---|---|
| 1,234,567 | UGX 1.2M | UGX 1.2M | **UGX 1.23M** |
| 2,500 | UGX 2K | UGX 2K | **UGX 2.50K** |
| 2,500,000,000 | **UGX 2.50B** | UGX 2.5B | UGX 2.50B |

`finance_operating_views.format_ugx_compact` carried the docstring *"same as
apps/frontend/views/budget_views.py"* — which was false at both the million and
billion scales.

All three also mishandled negatives: `val >= 1_000_000` is False for
−1,500,000, so it fell through to the uncompacted branch and rendered
"UGX -1500000" beside compacted positives.

**Fixed.** `apps/core/metrics/money.py` is now the one implementation; all three
modules import it. Precision is one decimal at M/B and none at K. Verified live
on `/fund-requests/weekly` and `/fund-approvals`.

The remaining nine copies (`projects/dashboard_service._fmt_ugx`,
`command_center/dashboard_service._ugx_compact_top` and a second nested copy,
`command_center/todo_service._country_budget_ugx`,
`analytics/cd_dashboard_service._ugx_compact`,
`analytics/pl_dashboard_service._ugx_compact`, `analytics/impact_engine._ugx`,
`frontend/views/dashboard_views._format_ugx_compact`, and the `ugx` template
filter) are listed as outstanding.

### 3.6 A page rendered one number twice under two names — FIXED

The PL Fund Approvals strip carried six tiles, two of which were the **identical
expression**:

```python
{"label": "Total Requested This Month", "value": _ugx(total_requested), ...}
{"label": "Planned Activities Funding", "value": _ugx(total_requested), ...}
```

Confirmed live: both rendered UGX 1.8M. This is the decorative duplication
section 7 requires be removed, and it is invisible in review because each tile
looks correct on its own.

**Fixed.** "Planned Activities Funding" removed; five tiles remain, each
answering a different question (scale, pending action, progress today, returns,
unit cost).

### 3.7 A leadership tile overstated reach by the whole portfolio — FIXED

The Admin dashboard's **"Schools Impacted"** was bound to `total_schools` —
every school in scope — under the helper *"total reached"*. On the seed it read
**702** where **261** schools had any completed work.

`AnalyticsDashboardService` already publishes "Schools Impacted" as *distinct
reached schools*, with the same label **and the same helper text**. So one
phrase meant two different things on two leadership surfaces, and the one that
overstated was the one an Admin lands on.

**Fixed**: now counts distinct schools with work in `COMPLETED_WORK_STATUSES`,
helper `"reached, of 702 in scope"` — the portfolio is kept as context rather
than passed off as the achievement.

### 3.8 A tile named a target it does not measure — FIXED

**"Country Target Achievement · vs last quarter"** computed
`completed_this_month / activities_this_month`. It compares nothing to last
quarter, and it measures no target — `CDAnalyticsService` owns the weighted,
validated target achievement, so the same phrase carried two different numbers.

**Fixed**: **"Country Activities Completed This Month"**, helper
`"200 of 221 scheduled this month"` — the denominator is now on the card.

Putting the denominator there exposed a second defect: `.admin-kpi small` was
`white-space: nowrap` with an ellipsis, so in a seven-column grid the helper
clipped to *"200 of 221 schedule…"* — the one detail that makes a percentage
auditable was the one being thrown away. It now wraps to two lines and clamps,
so the card keeps a bounded height without truncating mid-word.

Its numerator also filtered on a local `["completed", "ia_verified"]` pair,
silently excluding `closed` and `accountant_confirmed`. Both sets agree on
today's data so no number moved, but the next activity to reach either status
would have stopped counting as finished work — the regression
`apps/core/activity_types.py` exists to prevent. Now uses the canonical set.

### 3.9 The dashboard built 60 queries of figures it threw away — FIXED

`dashboard_view` called `DashboardMetricsService.get_dashboard_metrics(user)` at
the top of the view. Every role except the generic fall-through returns from its
own branch with its own numbers, and three roles redirect away entirely — so
for all of them the build was discarded.

Measured on the seed:

| Role | Before | After | Saved |
|---|---|---|---|
| CCEO | 212 ms / 131 q | 134 ms / 80 q | −51 queries |
| Country Director | 634 ms / 305 q | 532 ms / 245 q | −60 queries |
| Program Lead | 514 ms / 204 q | 434 ms / 144 q | −60 queries |
| **Accountant** (redirect) | 82 ms / 70 q | **3 ms / 2 q** | −68 queries |
| RVP | 484 ms / 306 q | 415 ms / 246 q | −60 queries |

**Fixed**: the three redirects moved above the page-data build, and the metrics
build moved down to its only reader. `apps/frontend/test_dashboard_metric_cost.py`
pins the ordering by asserting the service is never called, rather than by a
flaky wall-clock threshold.

### 3.10 Three of four KPI branches in the command centre are unreachable — REPORTED

`DashboardMetricsService.get_dashboard_metrics` builds `kpi_items` in four role
branches: CCEO, Program Lead, CD/RVP/Admin, and Accountant. Its
`kpi_strip_items` are read in exactly one place — the fall-through context of
`dashboard_view`. But CCEO, Program Lead and Accountant all return before that
line (the Accountant redirects; the other two render their own dashboards). So
**only the CD/RVP/Admin branch can ever render, and only for Admin.**

The other three branches — roughly 16 tiles — are unreachable. Two carry
mislabels that are consequently invisible rather than harmful:

* **"Schools Visited"** is bound to `ready_count`, which excludes schools by
  `planning_readiness`. That is data hygiene, not fieldwork.
* **"Evidence Pending"** is bound to `without_ssa_count` — schools without a
  current-FY SSA. SSA is structured score data, not evidence; conflating them
  is the distinction `docs/` records as previously corrected.

Left in place rather than deleted: removing three branches of a live service is
a judgement about future intent, and the runtime cost is already gone (§3.9).
They should be deleted or wired up deliberately.

## 4. What was built

### `apps/core/metrics/` — the canonical registry

Modelled on the existing `JOB_REGISTRY` convention.

- **`states.py`** — the six data states (`MEASURED`, `NO_DATA`,
  `NOT_APPLICABLE`, `NOT_YET_MEASURABLE`, `INSUFFICIENT_DATA`,
  `CONFIGURATION_REQUIRED`) and `MetricValue`, which **cannot** hold a number
  and an absence at once: constructing `MetricValue(NO_DATA, value=0)` raises.
- **`spec.py`** — `MetricSpec`. A percentage without a denominator, a money
  metric without a finance stage, or a tile with neither drill-down nor a stated
  reason for having none, all fail at construction.
- **`registry.py`** — `METRIC_REGISTRY` plus `check()`, which rejects duplicate
  keys, two metrics sharing a label, and labels from the ambiguity blocklist
  ("total", "budget", "pending", "performance", …).
- **`payload.py`** — `render_metric` / `render_strip`. `render_strip` **refuses
  to emit the same metric twice in one strip**, with a named-exception list so
  an exception is argued per metric rather than switched off per page.

### Presentation

`templates/components/kpi_strip.html` now emits `data-metric-key`,
`data-metric-period`, `data-metric-scope`, `data-metric-state` and
`data-component="kpi-card"` — the attributes the mandate's duplication detection
requires — but **only** when an item genuinely carries a registered identity.
Stamping a placeholder would make an unregistered tile look audited.

Absent tiles get an accessible sentence ("*My Completed Share of Planned Work:
No data.*") instead of a bare glyph, and a muted, non-tabular type treatment so
a reason does not read as authoritatively as a measurement.

### Migration: My Plan

My Plan's eight-tile strip is migrated end-to-end. Verified in the running app:
every tile carries its key, period, state and drill-down; and a period with
nothing planned now renders **"No data"** where it previously rendered **"0%"**.

Note the four period tiles were **kept**. Section 7 of the mandate explicitly
permits period-scoped repetition ("Month, Quarter, Mid-Year and FY are
meaningfully different"), so they are not duplicates under its own rules.

`Completion Readiness` → **`My Completed Share of Planned Work`**: the old label
named neither the numerator nor the period.

## 8. Outstanding — the mandate is **not** complete

This is a foundation plus one migrated page, not a finished platform sweep.
Stated precisely so the remaining work is not mistaken for done:

1. **~273 of 281 tiles are still unregistered.** Only My Plan's 8 are migrated.
   Every other page still builds bare dicts with no key, period, scope or data
   state.
2. **Five separate `_pct` helpers, 70 call sites** — `ia_views`,
   `dashboard_views`, `pl_analytics_service` and `hr/performance_engine`, plus
   `debriefs._pct_delta`. Three return `0` for an empty denominator; **the HR
   one returns `None`** — the correct behaviour already exists in the codebase,
   in one place, and three copies get it wrong. Each needs converting to
   `MetricValue.ratio`. The `/fund-requests/weekly` strip still shows four
   separate "UGX 0" tiles that all really mean "nothing in this state yet".
3. **Nine more compact-UGX formatters remain** (listed in 3.5), and **16 label
   families** are still computed in more than one module:

   | Label | Modules |
   |---|---|
   | Total Requested This Month, Awaiting Approval, Returned for Review | `budget_views` / `pl_approval_service` |
   | Accountability Pending | `budget_views` / `professional_development.services` |
   | Evidence Pending | `command_center` / `projects.dashboard` / `projects.my_plan` |
   | Planned This Week, Planned This Month | `command_center` / `projects.my_plan` |
   | Scheduled This Week | `command_center` / `projects.planning` |
   | Pending Approvals | `command_center` / `leave_views` |
   | Schools Impacted | `analytics_dashboard` / `command_center` |
   | Teachers Trained | `analytics_dashboard` / `projects.dashboard` |
   | High-Risk Staff | `accounts.hr_dashboard` / `targets.team_targets` |
   | Partner Activities, Total Projects | `projects.dashboard` / `projects.my_plan` / `projects.impact` |
   | SSA Required | `planning.planning_service` / `projects.planning_service` |
   | Returned | `ia_views` / `projects.my_plan` |

   Some of these are legitimate **role-scoped** repetition under section 6 (a
   PL's approval queue and the country budget page genuinely answer different
   questions). But each is currently *two independent computations*, so they
   can drift apart even where the repetition is justified. The registry
   resolves this by naming one owning service and listing approved secondary
   pages — the decision each pair needs is "one metric, or two names?"
4. **`raw_value` is dead on 56 tiles.** No template, view or script reads it.
   Dropped on My Plan; still carried elsewhere.
5. **The My Plan / Projects date-basis divergence is declared, not reconciled.**
   Reconciling needs a data-repair pass over the stored `quarter` field.
6. **Drill-down agreement is unproven.** Only 11 of 281 tiles have a drill-down
   at all; no test yet asserts that a tile's count equals the row count of what
   it links to.
7. **Not yet examined**: role-scope correctness across all 10 roles, cache-key
   role safety, real-time refresh after domain events, 15k-scale KPI timings,
   and the 295 hand-rolled stat blocks in 127 templates outside the shared
   component.

Items 1–4 are mechanical and safe. Item 5 is a data question. Item 6 is where
the next real correctness bugs are most likely to be, because a KPI that
disagrees with its own drill-down is the failure users notice and lose trust
over.
