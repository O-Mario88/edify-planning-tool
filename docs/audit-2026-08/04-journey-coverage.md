# End-to-end journey coverage (mandate §29, acceptance gate 3)

All 16 mandated journeys were traced through the code and
matched against the test suite.

**Verdict of the trace: not one journey was walked end to end.** The suite
covers the steps well and the seams barely at all — each half of a journey
fabricates its neighbour's outcome, so both halves pass while the handoff
between them is untested.

Journey 1, the platform's primary spine, now has a real end-to-end test
(`apps/core/tests/test_journey_school_visit.py`) that fakes nothing and
proves a weekly-advance-funded visit can be executed, verified, accounted
for and closed — the sweep's sharpest open question. The remaining fifteen
are scoped below, each with the specific gaps the trace found.

This is the backlog for gate 3. A journey is only closed when one test
walks it without hand-setting a status its neighbour should have produced.

## 5. Leave and temporary coverage: request → approval → target rephasing → calendar block → temporary coverage → access transfer → approval-authority transfer → leave completion → access restoration

- **End-to-end test:** NONE
- **Verdict:** GAPS
- **Gaps:**
  - Notification of the pending request has no test at all: LeaveNotificationService.notify_leave_requested (apps/hr/leave_services.py:1692) is never called by any test — the notification-lifecycle test hand-fires the raw event instead, so the recipient set (supervisor + every HR user + CD when the requester is a PL) is unverified.
  - Escalation to HR is 'covered' only by inspect.getsource() string assertions (apps/core/tests/test_leave_continuity.py:94, :86). escalate_to_hr is never executed in a test, and no test attempts to APPROVE an escalated request — which is why the dead-end at apps/hr/leave_services.py:766 was never caught.

- **Defects noticed while tracing:**
  - An escalated leave request can never be approved — escalation to HR is a one-way trap that only permits rejection.
